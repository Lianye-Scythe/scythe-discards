# v0.1 介面檢視與重做建議

日期：2026-10-26。以下記錄 v0.1 的評估與遷移建議。使用者其後已授權實作，v0.2 已依此重整；驗證及最新狀態見 [開發與驗證紀錄](VALIDATION.md)。

方法：重新檢視現有淺／深色、窄視窗、popup 截圖與來源，再以獨立設定檔開啟 Chrome for Testing 156.0.8078.47 的原生效能設定頁對照。這是產品與視覺評估，不是完整的無障礙符合性審核。

## 結論

保留已驗證的卸載核心、資料模型、訊息契約及有用的操作流程；介面遷移到 React 時重新設計呈現。主設定頁需要整體重整資訊架構、寬度、密度與控制元件，popup 保留快捷操作的任務順序並重做元件細節。

目前版本有 Chrome 的藍色、中性背景與側邊導覽元素，但尚未形成一致的 Chrome 設定頁操作語言。前一輪功能、溢出及機械檢查通過，不足以證明這項視覺目標已達成；先前的視覺驗收過於寬鬆。

## 值得保留

- 一般／嚴格模式、網站白名單、分頁保護、暫停與恢復等行為，以及既有核心與測試。
- 「規則、網站例外、分頁狀態、紀錄」的概念分類；重新安排目的地及畫面，不必改變使用者的任務語言。
- Popup 聚焦目前分頁、網站白名單及暫停，功能範圍合適。
- 系統深淺色跟隨、手動覆寫及語意狀態色的機制。色彩角色可延續，實際元件樣式應依新基準校準。
- 真實的使用中／受保護／已卸載狀態及就近的輸入錯誤，不捏造省下的 RAM。

## 優先重做

| --- | --- | --- |
| 導覽與頁面結構 | 側欄呈現不同功能頁的外觀，實際只跳到同一長頁的錨點；選取狀態只在點選時更新 | 依任務分為設定、分頁、紀錄等真正目的地，或把單頁目錄明確設計成目錄並同步捲動狀態 |
| 比例與密度 | 寬卡片與大留白配上零散小字，規則、例外與清單佔滿長頁，主次不清 | 設定改為較窄的緊湊設定列；分頁管理使用獨立、適合比較與操作的清單區 |
| 控制元件 | 大型框線單選卡、原生 checkbox/select、手繪圖示及自製按鈕混用；與 Chrome 的設定列、開關和單選列缺少一致性 | 先建立一致的開關、設定列、單選列、表單、狀態及動作元件，再組頁 |
| 生效與儲存模型 | 規則需要儲存，外觀、白名單與暫停卻即時生效，使用者需記住不同操作的生效方式 | 統一規則並清楚呈現待儲存／已生效；若採 Chrome 式即時生效，對嚴格模式與縮短期限明示後果 |
| 分頁清單 | 只做基本列出，標題易截斷、狀態與可點操作都用藍色、刷新重建清單 | 獨立清單畫面，清楚區分狀態與操作，保留焦點與選取；React 用穩定 key 更新列，之後再依需求增加批次操作 |
| Popup | 快捷任務順序可保留，但加入、移除與已加入狀態的圖示不一致；缺少直接可辨的目前保護原因 | 狀態與動作分開；已加入顯示勾選／保護狀態，解除使用對應圖示，沿用主頁的元件規則 |

## 對照中的實際數據

在相同 1440px 寬視窗中：

- 原生 Chrome 的設定群組寬約 680px；目前本工具主內容內寬約 944px。
- 本工具規則區含區外說明約高 445px；即使白名單空白，分頁狀態區也從距文件頂約 866px 開始。
- 本工具主標題 28px、分區標題 17px，多處模式說明與備註為 12px。問題在於小字與寬鬆大區塊的組合，並非所有文字都應一律放大。
- 原生 Chrome 對照頁使用較集中的設定列、右側控制和條列式單選選項，整體密度與層級更一致。

互動實測也確認：聚焦分頁保護按鈕後，跨過一次 15 秒自動刷新，焦點從按鈕退回 `body`；直接捲到紀錄區後，側欄仍選取「卸載規則」。這兩點應納入新版介面驗收，而不只是調整外觀。

這些尺寸是本次 Linux 測試瀏覽器中的觀察值，不是必須照抄的像素規格；Windows 的字型與原生控制外觀仍需實機驗證。

## 遷移邊界

1. 沿用 `src/core/`、背景排程、Chrome API adapter、訊息資料型別及核心測試。
2. 先依真實 Chrome 參考確立新版頁面與元件基準；現有 `DESIGN.md` 是 v0.1 現況紀錄，不應把所有舊值當作新版必須保留的約束。
3. 使用 React 重建設定頁與分頁清單。搬資料與行為，不逐行翻譯現有 DOM 組裝程式或照搬舊版面。
4. 按需引入 shadcn/ui 的互動元件，套用一致的 Chrome 方向樣式；預設 shadcn 外觀本身不能完成這個視覺目標。
5. Popup 共用新版元件，保留目前分頁的快捷流程。
6. 分開驗證功能、互動持續性與視覺；保留既有核心測試，更新介面測試，做同尺寸 Chrome 對照及實際人工檢視。
